# ORDER-001 · 같은 주문을 다시 보내도, 주문은 한 건만

## 고객의 목소리 — 합성 시나리오

“주문 완료 화면이 안 떠서 한 번 더 눌렀더니 주문이 두 건 생겼어요.”

기존 데모 서비스는 요청마다 새 주문을 만든다. 응답이 느릴 때 같은 주문
요청이 재전송되면 중복 주문이 생긴다. 실제 고객사 장애 사례가 아니다.

## 현업의 개발 요청

**같은 주문 요청의 재전송은 기존 주문 결과를 돌려주고, 별도의 새 주문은
정상적으로 접수한다.** 고객에게 재전송이 어떻게 처리됐는지도 알려 준다.
버튼 비활성화만으로 해결하지 않고 서버에서도 중복 생성을 막는다.

## 경영진이 확인할 결과

| 상황 | 기존 동작 | 기대 결과 |
| --- | --- | --- |
| 같은 주문 요청을 동시에 2회 보냄 | 모의 주문 2건 | **모의 주문 1건, 두 응답의 주문번호 동일** |
| 응답을 못 받아 같은 요청을 재전송 | 주문이 추가됨 | 기존 주문 결과 반환 |
| 고객이 별도의 새 주문을 보냄 | 새 주문 접수 | **기존처럼 새 주문 접수** |

실제 결제·고객 데이터·배포는 없다. 주문 금액과 건수는 합성 예시이며,
매출 개선이나 개발 시간 단축 실적이 아니다.

## 완료 기준

| ID | 기준 |
| --- | --- |
| AC1 | `POST /api/orders`는 `Idempotency-Key` 헤더를 필수로 받는다. 값은 8~80자의 영문자·숫자·`_`·`-`만 허용하며, 누락·잘못된 값은 HTTP 400 / `INVALID_IDEMPOTENCY_KEY`다. |
| AC2 | 동일한 `checkoutId` + 동일 키 + 동일 주문 내용의 순차·동시 요청은 정확히 한 주문만 만든다. 첫 응답은 201 / `replayed:false`; 재전송 응답은 200 / `replayed:true`이며 주문번호가 같다. 동시 요청에서도 생성 작업을 먼저 예약하고 기다리는 방식으로 중복을 막는다. |
| AC3 | 동일 범위·키를 다른 `productId` 또는 `quantity`로 재사용하면 409 / `IDEMPOTENCY_CONFLICT`다. 진행 중인 요청과 충돌해도 기존 주문이나 결과를 변경하지 않는다. |
| AC4 | 다른 키는 별도의 새 주문이다. 다른 `checkoutId`는 독립된 범위이므로 같은 키를 써도 각자 주문이 생성된다. |
| AC5 | 기존 주문 검증을 유지한다. 잘못된 주문은 키를 소비하지 않는다. 수정한 유효 주문을 같은 키로 다시 보내면 정상 접수된다. 기존 상태 확인·목록 조회·404 동작을 유지한다. |
| AC6 | 고객 화면에서 새 주문 생성과 기존 주문 결과 재사용을 구분한다. 동일 요청 2회 전송 및 별도의 새 주문 시나리오를 실제 브라우저에서 확인할 수 있어야 한다. |
| AC7 | 실패를 명시적으로 보여 주고 로딩 상태를 표시한다. 일반 주문 버튼의 중복 클릭을 방지하되, ‘동일 요청 2회 전송’ 실험 버튼은 실제 동시 요청 두 개를 보내 서버 보호를 검증한다. |

## 범위 밖 / 운영 환경으로 가져가기 전

실제 결제·환불, 고객 데이터, 인증·권한, DB·외부 API·의존성 변경, 배포,
GitHub PR 생성·병합은 하지 않는다. 데이터는 단일 Node 프로세스의 메모리에만
존재한다. 재시작·다중 인스턴스·저장 기간은 보장하지 않는다.
운영 적용에는 영속 저장소의 원자성/고유 제약, 사용자 범위, 키 수명,
장애·재시도 정책, 결제 연동 검토가 별도로 필요하다.
