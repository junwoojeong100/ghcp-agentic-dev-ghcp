같은 주문 의도를 재전송하면 기존 주문 결과를 돌려주고, 별도의 새 주문이면 새 주문을 접수해야 합니다. 고객 문제는 응답이 늦거나 보이지 않아 다시 눌렀을 때 중복 주문이 생기는 것입니다. 합성 데모의 목표이며 실제 고객 장애 사례가 아닙니다.

**관찰:** 서버는 요청마다 주문을 만들고, 화면은 두 응답 중 하나만 실패해도 주문 목록을 갱신하지 않아 부분 성공을 잘못 보일 수 있습니다. 화면의 재사용 응답 기록도 모두 “새 주문 생성”으로 표시됩니다.

**제안 — 완료 기준과 구현·검증 계획:**
- `src/app.mjs`: 키 형식과 필수 여부를 검증하고, `(checkoutId, 키)`별 생성 작업을 먼저 예약해 동일 내용의 동시·순차 요청은 한 주문으로 처리합니다. 첫 응답은 201, 재사용 응답은 200으로 같은 주문번호를 반환합니다. 같은 범위·키에 다른 상품 또는 수량이면 진행 중에도 409로 거절하고 기존 결과는 보존합니다. 주문 검증에 실패한 요청은 키를 소비하지 않습니다. 상태·목록·404 동작은 유지합니다.
- `tests/app.test.mjs`: 키 누락·형식 오류, 동시/순차 재전송, 진행 중 충돌, 다른 키 및 다른 체크아웃, 잘못된 주문 후 같은 키 재사용, 기존 상태·목록·404 동작을 검증합니다.
- `public/app.mjs`: 일반 전송 중 중복 클릭을 막되 동시 전송 실험은 실제 요청 2개를 보냅니다. 각 응답의 성공·실패를 따로 기록하고 부분 성공에도 목록을 갱신하며, 요청 실패와 목록 조회 실패를 구분해 표시합니다. 초기 요청은 새 주문, 재전송은 같은 키, 별도 새 주문은 새 키라는 흐름을 분명히 해 첫 동작이 새 주문이어도 설명·건수가 어긋나지 않게 합니다.
- `public/index.html`: 새 주문과 기존 결과 재사용, 로딩·실패·부분 성공을 구분해 안내하고 두 실험 시나리오를 확인할 수 있게 합니다. 브라우저에서 동시 재전송과 별도 새 주문을 확인합니다.

**범위 밖:** 실제 결제·고객 데이터·배포·의존성 변경은 하지 않습니다. 메모리 저장은 단일 Node 프로세스 범위이며 재시작·다중 인스턴스의 안전성을 보장하지 않습니다. 운영 전에는 영속 저장소의 원자성·고유 제약과 키 수명, 장애·재시도 정책 등을 별도로 검토해야 합니다.

**승인 checkpoint:** 위 네 파일만 변경하는 범위를 사람에게 제안합니다. 아직 구현 승인은 아닙니다. 승인 후 `demo-implementer`에 이 기준으로 인계하고, 실제 테스트 및 브라우저 확인 후 출시 여부는 별도로 판단합니다.
