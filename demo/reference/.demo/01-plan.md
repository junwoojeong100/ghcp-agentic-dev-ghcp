**계획 제안 — 핵심 규칙:** 같은 고객 범위(`checkoutId`)에서 같은 주문 표식과 내용이 재전송되면 주문은 한 건만 만들고 기존 결과를 반환해야 합니다. 별도의 새 주문은 기존처럼 정상 접수해야 합니다.

**고객 문제와 완료 기준**

현재 `src/app.mjs`는 `Idempotency-Key`를 검증·기록하지 않아 동시 요청마다 주문을 생성합니다. `public/app.mjs`도 모든 성공 응답을 “새 주문 생성”으로 표시합니다.

| 기준 | 구현 계획 | 검증 계획 |
|---|---|---|
| AC1 | 키를 8~80자의 영문·숫자·`_`·`-`로 검증 | 누락·형식 오류가 400 / `INVALID_IDEMPOTENCY_KEY`인지 확인 |
| AC2 | `checkoutId + key`별 진행 중 Promise와 완료 결과를 메모리에 예약·보관 | 순차·동시 재전송이 201/false, 200/true이며 동일 주문번호·총 1건인지 확인 |
| AC3 | 최초 유효 주문의 `productId`, `quantity`를 고정해 다른 내용 재사용을 거부 | 진행 중·완료 후 충돌 모두 409 / `IDEMPOTENCY_CONFLICT`, 기존 결과 불변 확인 |
| AC4 | 다른 키 또는 다른 `checkoutId`는 독립 처리 | 각각 새 주문이 생성되는지 확인 |
| AC5 | 주문 검증을 키 예약보다 먼저 수행 | 잘못된 주문이 키를 소비하지 않고, 수정 후 접수되며 목록·상태·404가 유지되는지 확인 |
| AC6–7 | 재사용 여부, 로딩, 오류를 명시하고 일반 버튼만 처리 중 비활성화 | 실험 버튼이 실제 동시 요청 2개를 보내며 UI가 새 주문/재사용/실패를 구분하는지 확인 |

**허용 파일별 변경 계획**

- `src/app.mjs`: 키 검증, 원문 충돌 판정, 진행 중 예약 및 완료 결과 재사용, 상태 코드·오류 응답 구현
- `public/index.html`: 네이티브 컨트롤의 로딩·상태 표현에 필요한 최소 마크업 보강
- `public/app.mjs`: 버튼 상태 관리, 동시 재전송 유지, `replayed`별 응답 기록, 요청·목록 실패 표시
- `tests/app.test.mjs`: 키 검증, 순차·동시 재시도, 충돌 payload, 키 비소비, 독립 주문 및 기존 회귀 테스트 추가

**범위 밖:** DB·외부 API·결제·인증·의존성·CSS·배포는 변경하지 않습니다. 메모리 저장이므로 재시작, 다중 인스턴스, 키 수명과 분산 원자성은 보장하지 않으며 운영 적용에는 영속 저장소의 고유 제약과 장애 정책이 별도로 필요합니다.

**승인 체크포인트:** 이는 승인 전 제안이며 구현하지 않았습니다. 사람이 위 네 파일과 기준 범위를 승인한 뒤 `demo-implementer`가 구현·검증하도록 인계합니다.
